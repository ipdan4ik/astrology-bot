# SP5 — Gift-a-Friend (Подарок другу)

**Status:** Draft
**Date:** 2026-05-28
**Predecessors:** SP4 (Referral Links) — required for the generic `start_tokens` infrastructure.

## 1. Goal

Let a registered tenant customer gift a chosen amount of `package_credits` to another Telegram user. The gift is delivered as a `t.me/<bot>?start=<code>` deep link. The first Telegram user to open the link with `/start <code>` receives the credits (new user gets an Account auto-provisioned, existing user gets a top-up). Sender is debited at creation time; unclaimed gifts auto-refund on expiry.

The feature reuses the SP4 `start_tokens` table and dispatcher — the gift is a new `kind="gift"` in that registry, not a parallel system.

## 2. Non-goals

- No targeted gifts (no @username picker, no "send to user X who is already a customer"). All gifts are open links.
- No fixed-amount-only mode; sender always chooses the amount within bounds.
- No partial claims (single-use, one recipient claims the full amount).
- No revocation in v1 — sender cannot cancel a pending gift to get an early refund; they wait for expiry. (`gift.history_title` screen shows status but no actions.)
- No cross-tenant gifts; sender and recipient are scoped to the same `tenant_id` carried on the token.
- No worker-side scheduled refund sweep; refunds happen lazily on next sender interaction with `/gift`.

## 3. Product decisions (from brainstorm)

| Decision | Choice | Notes |
| --- | --- | --- |
| Recipient scope | Anyone via deep link | Mirrors SP4 referral UX; new users get auto-provisioned. |
| Sender debit timing | At creation, refund on expire | Prevents double-spend; refund is lazy. |
| Amount bounds | `1 ≤ amount ≤ min(sender.package_credits, 1000)` | Hard cap 1000 matches the SP4 reward-credits style. |
| Expiry | 30 days default; owner-configurable 1–365 | Per-tenant via `tenant_config["gift.expiry_days"]`. |
| Refund mechanism | Lazy sweep on sender action | Triggered when sender opens `/gift` or creates a new one. |
| Sender list | Yes — last 10 with status | Read-only history; no inline revoke. |
| Sender surface | `/gift` command + `btn.gift` reply-keyboard button | Symmetric with `/invite` (SP4). |
| SP4 schema | Drop `uq_start_token_uses_account_id` global UNIQUE | Per-kind handlers enforce their own uniqueness. |

## 4. Architecture

### 4.1 Data model

The feature stores everything in existing SP4 tables. **No new tables.**

`start_tokens` columns reused:

| Column | Gift semantic |
| --- | --- |
| `code` (PK, 8 chars) | Deep-link payload, generated by `generate_gift_code` (alphabet `[A-Z0-9]`, 5 retries on collision). |
| `kind` | `"gift"` (constant `GIFT_KIND`). |
| `tenant_id` | Carries the originating tenant; gift is only valid within that tenant. |
| `owner_account_id` | Sender. Indexed (SP4 already added the index). |
| `payload` (JSONB) | `{"amount": <int>}`. |
| `status` | `"active"` → terminal `"claimed"` or `"refunded"`. New values relative to SP4; column has no CHECK constraint so no DDL needed. |
| `max_uses` | Always `1`. |
| `used_count` | Bumped to `1` on claim. |
| `expires_at` | `now + tenant.gift_expiry_days days`. |
| `created_at` | Default. |

`start_token_uses` rows for gifts:

- `account_id` = recipient
- `token_code` = gift token's code
- `claimed_at` = set on insert (gifts claim immediately, unlike SP4 referrals where `claimed_at` is deferred to first paid spend)

### 4.2 Schema delta (SP4 ↔ SP5)

Single Alembic migration that **only drops the global unique constraint**:

```python
# alembic/versions/f2a3b4c5d6e7_drop_start_token_uses_account_unique.py
def upgrade() -> None:
    op.drop_constraint(
        "uq_start_token_uses_account_id",
        "start_token_uses",
        type_="unique",
    )

def downgrade() -> None:
    op.create_unique_constraint(
        "uq_start_token_uses_account_id",
        "start_token_uses",
        ["account_id"],
    )
```

The SP4 referral handler already does its own pre-flight SELECT for the "already attributed?" guard (`bot/handlers/start_tokens.py::handle_referral_token`), so removing the DB constraint changes no behaviour for referrals.

`StartTokenUse.__table_args__` in `src/quantuum/db/models.py` loses the `UniqueConstraint(...)` entry. After this migration there are no table-level constraints on `start_token_uses` beyond the FKs.

### 4.5 Domain layer (`src/quantuum/domain/gifts.py`)

```python
GIFT_KIND = "gift"
GIFT_CODE_LENGTH = 8
MAX_GIFT_AMOUNT = 1000
MIN_GIFT_AMOUNT = 1

async def create_gift(
    session, *, sender_account_id: int, tenant_id: int, amount: int
) -> StartToken:
    """Validate amount; debit sender; insert active token; audit gift.created.

    Raises:
      ValueError: amount out of [1, 1000]
      InsufficientCreditsError: sender.package_credits < amount
    All work happens in the caller's transaction; caller commits.
    """

async def list_recent_gifts(
    session, *, sender_account_id: int, limit: int = 10
) -> list[GiftRow]:
    """Return sender's last <limit> gift tokens with derived status.

    GiftRow is a small dataclass: code, amount, status, expires_at, claimed_at, claimed_by_tg_user_id (None if unclaimed).
    Status derivation:
      - status='claimed'   if token.status == 'claimed'
      - status='refunded'  if token.status == 'refunded'
      - status='active'    if token.status == 'active' and expires_at > now
      - status='expired'   if token.status == 'active' and expires_at <= now (will be refunded on next sweep)
    """

async def sweep_expired_gifts(
    session, *, sender_account_id: int
) -> int:
    """Find active+expired+unclaimed gifts for this sender; refund each.

    For each candidate (with FOR UPDATE SKIP LOCKED via SELECT):
      - bump sender.package_credits by payload['amount']
      - set token.status='refunded'
      - audit gift.refunded with reason='expired'
    Returns number of gifts refunded.
    Caller commits.
    """

async def get_expiry_days(session, *, tenant_id: int) -> int
async def set_expiry_days(session, *, tenant_id: int, days: int, by_account_id: int) -> None
async def reset_expiry_days(session, *, tenant_id: int, by_account_id: int) -> None
```

Code generation uses a private `generate_gift_code(session, *, owner_account_id, tenant_id)` that follows the same pattern as `generate_referral_code` (random A-Z0-9, 5 retries, warn-then-raise on collision exhaustion).

### 4.6 Dispatcher (`src/quantuum/bot/handlers/start_tokens.py`)

Add a gift handler and register it. `dispatch_start_token`'s signature changes to return an optional **dispatch result** so `/start` can surface kind-specific confirmation messages (referral handler keeps returning `None`).

```python
@dataclass
class GiftClaimResult:
    amount: int

async def handle_gift_token(
    session, *, token: StartToken, account_id: int
) -> GiftClaimResult | None:
    # Self-gift guard (silent + audit).
    if token.owner_account_id == account_id:
        await write_audit(session, action="gift.self_blocked", ...)
        return None

    # Feature flag check (silent reject if tenant has gifts off).
    if not await is_feature_enabled(session, token.tenant_id, "gifts"):
        return None

    amount = int(token.payload.get("amount", 0))
    if amount <= 0:
        # Malformed payload; refuse silently.
        return None

    # Take a row lock on the token to serialize concurrent claims.
    locked = (
        await session.execute(
            select(StartToken).where(StartToken.code == token.code).with_for_update()
        )
    ).scalar_one()
    if locked.status != "active" or locked.used_count >= locked.max_uses:
        return None  # Lost the race; somebody else claimed it.

    # Claim row + credit recipient + close token in one transaction.
    session.add(StartTokenUse(token_code=locked.code, account_id=account_id, claimed_at=utcnow()))
    bal = await session.get(AccountBalance, account_id)
    bal.package_credits += amount
    locked.status = "claimed"
    locked.used_count = 1
    await write_audit(session, action="gift.claimed", actor_account_id=account_id, ...)
    return GiftClaimResult(amount=amount)

_HANDLERS[GIFT_KIND] = handle_gift_token
```

`/start` updates: capture the dispatch result and, when it's a `GiftClaimResult`, send `gift.received` (with `{amount}`) before the existing welcome message. The SP4 referral handler's `None` return is unchanged so no SP4 behaviour shifts.

The `/start` flow already pipes the payload through this dispatcher (SP4 Task 4). New users are auto-provisioned by the existing `AccountMiddleware` **before** dispatch runs (verified at `src/quantuum/bot/handlers/start.py:21` — `account: Account` is middleware-injected; the existing `AccountBalance` row is seeded with welcome credits by `find_or_create_account_by_tg`), so a gift claimed by a brand-new Telegram user works the same as a referral.

### 4.7 Sender UX (`src/quantuum/bot/handlers/gift.py`)

Router exposes:

1. `@router.message(Command("gift"))` and `@router.message(F.text.in_(_GIFT_LABELS))` — both call `show_gift_screen(...)`.
2. `show_gift_screen(message, *, account_id, tenant_id, i18n)`:
   - Feature-flag check → `gift.disabled` if off.
   - `await sweep_expired_gifts(session, sender_account_id=account_id)` then commit.
   - Render: title, balance line, recent gifts (last 10 with status), and an inline "Create new gift" button → callback `GiftCreateCb()`.
3. FSM `Gift.awaiting_amount`:
   - Entry callback prompts "Введите сумму (1–{max})" where `max = min(balance, 1000)`.
   - Text handler validates integer, range; on success calls `create_gift(...)`, commits, replies with the deep link + share-URL inline button.
   - Cancel handler (`/cancel` or `cancel` text) clears state with `gift.cancel_hint`.

The share-URL inline button uses `https://t.me/share/url?url=...&text=...` exactly like `/invite`, with `gift.share_text` as the suggested caption.

### 4.8 Owner UX (`src/quantuum/bot/handlers/owner_console.py`)

Mirror SP3 Branding / SP4 Referrals: add a `Gifts` button to the `/manage` keyboard, callback `OwnerGiftsCb(action="open" | "edit" | "cancel" | "reset", tenant_id=...)`. Handlers:

- `on_gifts_open`: show current expiry days, edit / reset / cancel buttons.
- `on_gifts_edit`: enter FSM, prompt for new value (range hint included).
- `on_gifts_value`: validate, call `set_expiry_days`, exit FSM, show saved confirmation.
- `on_gifts_reset`: call `reset_expiry_days`, show reset confirmation.
- `on_gifts_cancel`: exit FSM, return to submenu.

All four follow the SP3 pattern: `query: CallbackQuery, callback_data: OwnerGiftsCb, i18n: Translator` (+ `state` where needed); extract `tg_user_id = str(query.from_user.id)`; call `authorize_tenant_action(session, tg_user_id, callback_data.tenant_id)`; `state.update_data(tenant_id=callback_data.tenant_id)` for the edit path; re-authorize via `message.from_user.id` on FSM text input.

```
Recipient opens t.me/<bot>?start=<CODE>
  │
  ▼  (existing SP4 path)

  │
  ▼
```

### 5.3 Refund flow (lazy)

```
Sender taps "btn.gift" or "/gift"
  │
  ▼
show_gift_screen() →
sweep_expired_gifts():
  SELECT codes WHERE owner=? AND kind='gift' AND status='active' AND expires_at < now()
  for each:
    bal.package_credits += payload['amount']
    token.status = 'refunded'
    audit gift.refunded(reason='expired')
  commit
  │
  ▼
History shows the just-refunded entries with status='refunded'
```

## 6. Concurrency & abuse considerations

- **Double-claim race:** The dispatcher claim is wrapped in the request transaction. Two concurrent `/start` calls for the same code race on `start_token_uses` insertion (no longer protected by UNIQUE), so we additionally check `token.status == "active"` and `used_count < max_uses` inside the handler under `SELECT … FOR UPDATE` on the token row. Whichever transaction acquires the row lock first wins; the loser sees `status="claimed"` and aborts silently.
- **Self-gift via second Telegram account:** Not detectable without device fingerprinting; out of scope. The amount caps + tenant feature toggle let owners control blast radius.
- **Code collision:** `generate_gift_code` retries 5x; logs warning and raises `RuntimeError` on exhaustion (matches SP4 referral path).
- **Tenant boundary:** `resolve_start_token` already filters on `tenant_id`. A code generated in tenant A is invisible to bot for tenant B.
- **Refund during simultaneous spend:** `sweep_expired_gifts` and `consume_quota` both touch `AccountBalance.package_credits`. Both run in their own transactions; sweep takes the row update with the normal SQLAlchemy auto-flush — last-writer-wins is acceptable here because refund only adds (no negative balance possible).
- **Malformed payload:** Gift handler asserts `amount > 0`; out-of-range payloads silently abort (covers manual DB tampering).

## 8. Out-of-scope follow-ups

- **Worker-side global sweep cron** — could refund gifts that nobody comes back to. Defer until support tickets warrant.
- **Revoke action on pending gifts** — straightforward to add later (one extra callback + handler), users explicitly deferred.
- **Targeted gifts (by @username)** — would need a username-→-account resolver and a confirmation hop. Skipped per brainstorm.
- **Per-tenant max gift cap** — currently hard-coded at 1000. Could move into `tenant_config` if a tenant asks.
- **Multi-recipient gift codes** — `max_uses > 1` is in the schema but not exposed in v1.
